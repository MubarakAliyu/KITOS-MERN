# KITOS 2.0 — 10-minute demo script

For the recorded walkthrough. Timings are cumulative and assume no fumbling; the content is sized
for about nine minutes so there is room to breathe.

---

## Before you press record

**Open the live site two minutes beforehand and sign in once.** Render's free tier sleeps after
fifteen minutes idle and takes 30–50 seconds to wake. The client shows a "Waking the server…"
notice so the wait is legible, but a demo should not open with it.

Then:

- [ ] **Re-run the seed.** The demo session is placed in a 60-minute window from the moment the
      seed runs (ADR-028), so a session seeded yesterday is no longer live today, and the QR
      check-in section will not work. This is the single most common way this demo breaks.
- [ ] Two browsers, or one plus an incognito window — the chat section needs two people signed in
      at once. Put them side by side before recording.
- [ ] Sign out of everything in the main browser; the first thing on screen should be the sign-in
      page with the KIT logo.
- [ ] Have the credentials on a card off-screen. Typing a wrong password on camera costs thirty
      seconds and composure.
- [ ] Close every other tab. A notification from elsewhere in a recording is a re-record.
- [ ] If `FLW_SECRET_KEY` is set, have a Flutterwave **test card** to hand. If it is not, the
      payment runs in simulated mode — **say so out loud** rather than letting it look like a live
      charge.

---

## 0:00 — The problem (60 seconds)

Nothing on screen but the sign-in page, or a photo of a KIT bootcamp.

> "Kids In Tech is a StarNova Labs programme teaching coding and robotics to children aged eight to
> eighteen, in Sokoto and Birnin Kebbi. Three cohorts, more than a hundred and eleven children
> trained.
>
> The bootcamps work. The problem is what happens after one ends: the learning stops. There is no
> way for a child to continue, no way for a parent to see progress, and no way for an instructor to
> keep teaching between cohorts.
>
> KITOS is the system that fills that gap. The interface was already designed and built — what it
> had was mock data and a PHP API that could not be deployed. This project gave it a real backend
> on the MERN stack, and put it in the cloud."

Say the honest version of the starting point: a complete frontend, no working backend.

## 1:00 — Architecture (90 seconds)

Show the diagram from `docs/DEPLOYMENT.md`.

> "Next.js on Vercel. An Express API with Socket.IO on Render. MongoDB Atlas in Frankfurt —
> the closest region to Nigeria. Cloudinary for uploads, because Render's disk is wiped on every
> deploy. Flutterwave in test mode for fees.
>
> The server is layered: route, controller, service, model. Business rules live only in services,
> which is why they can be tested without an HTTP layer — there are 542 server tests.
>
> Two things are worth naming now, because they shape everything else. Money is stored as integer
> kobo and never as a float. And permissions are a single matrix plus an ownership check inside the
> service: hiding a button in the interface is not security, so every route is checked twice."

## 2:30 — A parent enrols a child (60 seconds)

Sign in as the parent.

- Add a child: name, date of birth, track. Point out there is **no email field** — a child under
  eighteen does not need an account of their own to be reachable.
- Show the consent record being written.
- The child appears with an admission number, `KIT/26/00N`, generated by the server.

> "No student email, parental consent recorded with the time, the IP and the user agent, and the
> account stays pending until a parent approves it. Those are child-safety requirements, not
> features."

## 3:30 — The child learns (90 seconds)

Sign in as the student with the **admission number**, not an email.

- Open a course, play a lesson, mark it complete — watch the progress bar move.
- Take a quiz; show the score.
- Submit an assignment.
- Open **Certificates**: one was issued the moment the last item was finished.
- Click **Verify** and show the public verification page.

> "Progress is recomputed from what the child has actually done, never stored as a number someone
> could set. The certificate issues itself when the course completes — whether the last thing
> finished was a lesson, a quiz or an assignment. And it verifies at a public URL, so an employer
> or a secondary school can check it without an account."

## 5:00 — The instructor teaches (60 seconds)

Sign in as the instructor.

- Show the session list; one session is **live** right now.
- Open it and show the **QR code** for check-in. Note the token refreshes every 60 seconds.
- Mark a pupil present; show the roster updating.
- Open **Submissions**, leave feedback on the assignment the student just submitted.

> "The session's status is computed from the clock, not stored — so nothing has to run on a
> schedule to make a class 'live', and a sleeping free-tier server cannot miss it. The QR token
> lasts sixty seconds, so a photograph of the screen is useless a minute later."

## 6:00 — Chat, and the rule it exists for (60 seconds)

Both browsers visible.

- Instructor and parent exchange a message — it arrives instantly, no refresh.
- Switch to the parent's view of their **child's** conversation: readable, with the composer
  disabled.
- Then the important part: show the API refusing a student-to-student message (the network tab, or
  the prepared `curl`).

> "Student to student is not hidden in the interface — it is refused by the API, with a 403. A
> parent can read every conversation their child is in and cannot write in it: reading is the
> safeguarding requirement, writing as them would be impersonation.
>
> This is an allow-list, not a deny-list. A pair that nobody explicitly permitted is refused by
> default."

## 7:00 — A payment (60 seconds)

Back to the parent.

- **Pay Now** → choose child and course → confirm. Show the Flutterwave step.
- Complete it; the receipt appears with an `RCP-` number. Download the PDF.
- Show the enrolment is now active.

> "The amount never comes from the browser. The modal sends one because the original mock did, and
> the server ignores it and charges the course fee — otherwise anyone could pay one naira for a
> twenty-thousand-naira course.
>
> And the confirmation happens exactly once. Flutterwave tells us twice — once when the browser
> returns, once by webhook — and sometimes in the same millisecond. A single atomic claim decides
> which one does the work, so there is one receipt and one enrolment, never two."

If running simulated: *"There are no Flutterwave keys on this deployment, so this is the simulated
gateway — the receipt says DEMONSTRATION PAYMENT on its face, deliberately."*

## 8:00 — Admin, deployment and CI (60 seconds)

Sign in as the admin.

- Dashboard tiles and the four charts — point out they reflect everything done in the last ten
  minutes.
- The **activity log**: every action from this demo is in it.
- Then the dashboards: Render (the service and `/health`), Vercel, Atlas, and the GitHub Actions
  run going green.

> "Every figure is computed from the collections, not cached — an administrator asking 'what is
> true now?' should not be shown a number that was true once.
>
> Every admin action writes an append-only audit row. And CI runs lint, 542 server tests, the
> Playwright suite on desktop and a Pixel 7, and an accessibility sweep over every role's screens,
> on every push."

## 9:00 — Results and what is next (60 seconds)

> "What works: four roles end to end, real-time chat with the child-safety rules enforced server
> side, payments that confirm exactly once, verifiable certificates, and the whole thing deployed
> on free tiers.
>
> What is honest about the limits: Flutterwave is in test mode, so no real money moves. The Hausa
> translation ships unreviewed by a native speaker and is marked as such. The free tier sleeps, so
> the first visit after an idle period takes about forty seconds. And the light theme does not meet
> AA contrast — we measured it, 47 colour pairs, and it needs a palette decision rather than a
> patch, so it is written up rather than quietly left.
>
> Next: a native-speaker pass on the Hausa, the light-theme palette, and offline-first lessons —
> because connectivity in Sokoto is the real constraint on all of this."

## If something goes wrong on camera

| Problem | Do this |
|---|---|
| The first page takes 40 seconds | Say "that's the free tier waking up" and keep talking. It is a true and interesting fact about the architecture. |
| The session is not live | You did not re-seed. Skip to submissions; do not debug on camera. |
| Chat does not arrive | Check both browsers are actually signed in as different people. Fall back to showing the refusal, which is the more important half. |
| A payment fails | Check `FLW_SECRET_KEY`. If it is set and the card is declined, that is a real Flutterwave test-mode result — say so and move on. |

Record in one take if you can. A ten-minute demo with one recovered stumble is better than a cut
that loses the thread.
